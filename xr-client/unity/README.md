# xr-client/unity

The headset app. Since 2026-10-30 this is the way forward ([docs/xr-client-strategy.md](../../docs/xr-client-strategy.md)); the web app in `../pages/` is only a reference for porting.

| Phase | What | Status |
|---|---|---|
| 0 | Project skeleton: URP, OpenXR + Android XR, empty scene with a placeholder video window and an fps readout, builds to an APK | done (2026-10-28: runs on the Galaxy XR, OpenXR session focused, Vulkan on the Adreno 740, steady 72 fps / 13.9 ms without video) |
| 1 | Video spike: robot camera via `com.unity.webrtc` (daemon signalling on the LAN), fps + latency against the web app (34 fps, 233 ms) | done (2026-10-30, real robot): **VR 72 fps**, video 60 fps, latency **median 141 ms** with the flash test, over Wi-Fi ([latency.md](../../docs/measurements/latency.md)). The web app's 233 ms came from the QR method on one Mac, so the two numbers are not a strict comparison |
| 2 | Head-pose loop: port `pose.js`, targets and measured pose directly from the daemon | done (2026-10-30, real robot): Reachy follows the head, targets sent at 72 Hz. Follow lag not measured yet |
| 3 | World-locked reprojection: port `camera.js` (video sphere, lens model) | done (2026-10-30, real robot): tried in the headset, comfortable after the pose fix below |
| 4 | Feature parity, in this order: audio, captions, speaker following, panorama with a short scan, notes, sign-in, depth | audio working (2026-10-30), still to be tried in a separate room |

## Setup

- **Editor:** Unity **6000.6.7f1** with **Android Build Support** (incl. OpenJDK, Android SDK & NDK), installed through Unity Hub.
- **Target:** Samsung Galaxy XR (Android XR). Quest comes later: the OpenXR *Meta Quest Support* feature is not on yet.

Open `xr-client/unity` in Unity Hub (Add → project from disk). The project is generated by three editor scripts in `Assets/Editor/`, so every setting is in code:

| Script | Does |
|---|---|
| `ProjectSetup.AddPackages` | Adds the packages (URP, Input System, XR Management, OpenXR, Android XR, XR Interaction Toolkit, WebRTC). The Package Manager picks the versions verified for this editor. |
| `ProjectConfigure.Run` | URP asset (HDR and post processing off, as Android XR requires); Android player settings (IL2CPP, ARM64, API 32+, Vulkan, Game Activity, Input System); OpenXR loader with Android XR support and the hand, Khronos-simple and Touch controller profiles; `Assets/Scenes/Main.unity`. |
| `ProjectBuild.Android` | Development APK → `Builds/ReachyMeetings.apk` |

Run from the repo root:

```bash
UNITY=/Applications/Unity/Hub/Editor/6000.6.7f1/Unity.app/Contents/MacOS/Unity
```

```bash
$UNITY -batchmode -projectPath xr-client/unity -buildTarget Android -executeMethod ProjectConfigure.Run -quit -logFile -
```

```bash
$UNITY -batchmode -projectPath xr-client/unity -buildTarget Android -executeMethod ProjectBuild.Android -quit -logFile -
```

The Unity editor must be closed for batch mode on the same project.

## Install on the Galaxy XR

Enable developer mode (Settings → About → Software information → tap the build number 7 times) and USB debugging. Connect the Mac to the **hidden USB-C port on the right side of the headset** (press the round mark on the cover to pop it open; data only, power still comes from the battery pack), not to the battery pack. Accept *Allow USB debugging?* in the headset (if it does not show: Developer options → Revoke USB debugging authorizations, replug). Then:

```bash
ADB=/Applications/Unity/Hub/Editor/6000.6.7f1/PlaybackEngines/AndroidPlayer/SDK/platform-tools/adb
```

```bash
$ADB install -r xr-client/unity/Builds/ReachyMeetings.apk
```

The app appears in the launcher as *Reachy Meetings*. You should see a dark-blue room, a floor, a window 2 m ahead at eye height (checkerboard until video arrives), and the frame rate and video status below it.

## Robot video (Phase 1)

The app connects straight to the daemon's WebRTC signalling on the robot laptop (`ws://<laptop-ip>:8443`, GStreamer `webrtcsink`, the same as `../web/index.html`), not through HF sign-in and Pollen central. Headset and laptop must be on the same Wi-Fi. Tell the app the address once; it is remembered on the headset:

```bash
$ADB shell am start -n ch.ethz.reachymeetings/com.unity3d.player.UnityPlayerGameActivity -e signalling ws://<laptop-ip>:8443
```

- **Real robot:** the daemon (Reachy Mini Control) must be running with media on. Its signalling server listens on all interfaces, also with the default `--localhost-only`.
- **Without the robot:** `robot/scripts/fake_camera.py` (see robot/README.md) sends a 1080p60 test pattern with the same signalling and codec, plus a time strip: the app then also shows the video latency.

**Audio is declined by default.** libwebrtc delays video to stay in sync with the audio track, and this app does not play it: 141 ms without, 302 ms with (`-e audio on` on the `am start` line, for A/B tests). Sending the mic to the robot in Phase 4 will need that transceiver as send-only instead of inactive.

- **Real latency:** `robot/scripts/flash_clock.py` on the robot laptop, with its screen in the camera's view.

**Debugging over Wi-Fi:** Developer options → Wireless debugging → pair once (`$ADB pair <ip>:<pairing-port> <code>`; the port and code are on the pairing screen), then `$ADB connect <ip>:<port>` with the port on the Wireless debugging screen. Installs take about a minute. If adb reports `more than one device`, use `-s <ip>:<port>`.

Status lines below the frame rate: connection state; incoming video (size, fps, bitrate, codec, decoder); jitter buffer delay, decode time per frame, dropped frames; latency (median, p10–p90, clock sync accuracy). All of it also goes to `adb logcat -s Unity` as `[stats]`, `[latency]` (fake camera) and `[flash]` (real camera).

## Controlling Reachy (Phase 2)

The app talks to the daemon on the laptop directly (port 8000, same host as the signalling URL), so `reachy-meetings` does not need to run: targets over `/api/move/ws/set_target`, measured pose from `/api/state/ws/full`, wake and sleep over HTTP. Reachy never moves by itself:

- **Pinch** (or trigger): wake if needed, take this as straight ahead, follow. Pinch again: recenter.
- To put Reachy to sleep, use Reachy Mini Control: closing the app leaves it awake, holding its last pose.

`Assets/Scripts/Pose/Pose.cs` is the port of `pose.js`, with no Unity in it. Tests in `Assets/Tests` compare it with values generated by running `pose.js`, and check the head-turn signs:

```bash
$UNITY -batchmode -projectPath xr-client/unity -buildTarget Android -runTests -testPlatform EditMode -assemblyNames ReachyPose.Tests -testResults /tmp/results.xml -logFile -
```

Every second, `adb logcat -s Unity` shows `[control]` with sent and measured angles. The daemon only answers `set_target` with errors; those appear in the log and on the status line.

## World-locked video (Phase 3)

The video sits on a piece of sphere around the eye, 3 m away, with every grid point in the direction its pixel sees (`CameraModel.cs`, our calibration from 2026-10-08). The sphere hangs where the robot camera looked when the shown frame was captured, so your own head turns show without lag and the robot's delay only shows as the window's edge.

**The window does not use the measured pose directly.** The first version did and caused nausea. The measured pose comes in stair-steps (16 % of the poses are exact repeats) and in Wi-Fi bursts, so the window jittered 0.24–0.29° per frame on a 0.37° step, and spiked to ~180–220 °/s while the robot turned at under 50 °/s. Now (`PoseBlend` in `ViewLogic.cs`) it is the commanded path, delayed by the robot's lag (255 ms), plus a slow correction towards the measured pose (time constant 0.5 s): jitter 0.044°, top speed 64 °/s, on average 1.3° from the true path (worst 5.5°). Measured poses are placed by the daemon's timestamps (`PoseClock`), not their arrival time.

The time the window looks back is the jitter buffer + decode from the WebRTC stats + 70 ms for capture and network (`CaptureDefaultMs`, an estimate). If the robot does not really follow (asleep, stuck, no poses), `FollowGuard` puts the window in front of you instead; the status line says `view world-locked` or `in front`.

**Bench test:** `-e sweep 1` on the `am start` line turns Reachy's head ±30° for 24 s by itself and records `sweep.csv` and `sweep.poses.csv` in the app's files folder. The headset must be worn, or it sleeps: close your eyes. Tuning without a rebuild: `-e lagms`, `-e capturems`.

**Headset sleep:** the app closes itself after ~2 s asleep (`AppLifecycle.cs`), because a paused app could not be reached again after waking. Open it again from the launcher: the address is remembered, and Reachy waits for a pinch.

## Audio (Phase 4)

- **Your voice to Reachy:** the headset mic goes over WebRTC to the robot's speaker (`MicSender.cs`), only while Reachy follows you. The audio transceiver is send-only, so the video delay stays low (see *Audio is declined by default*). The first start asks for microphone access in the headset.
- **Room sound:** Reachy's mic array reaches the laptop over USB, and the backend streams it to the app (`BackendClient.cs`, `RoomSound.cs`, `RoomAudio.cs`: jitter buffer and speech filter, port of `roomaudio.js`).

Start the backend in **Terminal.app** the first time, so macOS can ask for microphone and camera access:

```bash
backend/scripts/start_for_headset.sh
```

It listens on the Wi-Fi with a secret (`~/.config/reachy-meetings/lan_secret`), so others on the network cannot listen in. Tell the app once, with the headset on:

```bash
$ADB shell am start -n ch.ethz.reachymeetings/com.unity3d.player.UnityPlayerGameActivity -e secret $(cat ~/.config/reachy-meetings/lan_secret)
```

**If the room sound is silent:** check `curl localhost:8000/api/audio/config/parameter/AUDIO_MGR_MIC_GAIN`. If it fails (`status 68`, `exceeds 100 times`), the robot's mic chip is stuck and sends digital silence: put Reachy to sleep and power-cycle it. Seen once on 2026-10-30, cause unknown.

## Scene

- `XR Origin` (floor tracking) → `Camera Offset` → `Main Camera`, with a Tracked Pose Driver on the headset pose.
- `Video Window`: the video sphere (`VideoWindow.cs`), built at runtime; the status text hangs below it.
- `Robot Video`: `Assets/Scripts/Robot/RobotVideo.cs` (peer connection, stats), `GstSignalling.cs` (webrtcsink signalling protocol, no Unity rendering), `VideoLatency.cs` (time strip, fake camera), `FlashLatency.cs` (flash test, real camera), `ClockSync.cs`, `RobotControl.cs` (pinch, following), `DaemonClient.cs` (daemon sockets).
- `Fps Label` (`Assets/Scripts/FpsLabel.cs`): fps and ms per frame, averaged over 0.5 s. Drawn with `Assets/Shaders/WorldText.shader`: the built-in text shader does not render both eyes with single-pass instanced stereo, and URP Unlit draws the alpha-only font atlas black.
